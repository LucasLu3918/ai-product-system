# System Improvement Review — Dev Friction PR10: Profile Switch Mechanism

- **Appropriateness:** Suitable. The approved plan needs one place where relaxations are defined, switched and made visible. Without it, PR11 would have to invent its own switch storage and the agent could be the one editing it.
- **User problem:** Relaxations such as the co-author trailer or a new topology import need a per-machine switch. Today there is none, so either every behaviour is hard-coded or a relaxation would be an unaudited file edit that an agent could make.
- **Proposed solution:** A fixed allow-list in code, a strict YAML file under the AIPS config home that fails closed to defaults with a bounded diagnostic, a `show` command, and a `set` command that needs an interactive terminal and an exact typed phrase. The PR3 guard denies the agent's Bash form of `set`. Turn Context and the publication doctor show the active profile as names and a reason code.
- **Reuse / lower-layer alternative:** Reuses the PR3 protected-path categories (`profile_settings_path`, `config_home`), the creative approval pattern (TTY check, typed phrase, atomic write, stderr summary) and the publication doctor. No daemon, database or new dependency.
- **Security / reliability:** Defaults are off and the allow-list is empty, so PR10 changes no behaviour. Unknown keys reject the whole file, so a typo can never partially enable a relaxation. A malformed or symlinked file never overwrites and is never followed. Writes are atomic with mode 0600 in a 0700 directory, and a failed replace leaves the previous file. Failures in the profile module degrade to strict defaults with an UNAVAILABLE marker and never block Turn Context or diagnostics.
- **Limitation:** The TTY gate is local. A process able to allocate a pseudo-terminal could imitate it; the guard's denial of the Bash form of `aips profile set` narrows this, and the host confirmation is still the authority. Interpreter-based writes (`python -c`) are not classified by the PR3 guard, as already documented.
- **Compatibility:** No profile file means no behavioural change. Turn Context gains one line and the doctor result gains one additive `profile` key. Two additive help lines update the pinned plan21 digest.
- **Constitution impact:** NO. No Human approval, publication, merge, secret or PII scanning, node trust or ComfyUI boundary changes. The mechanism is the human-only control that D8 requires; it grants no relaxation by itself.
- **Recommendation:** Adopt as PR10 of the approved plan; keep every switch off until PR11 adds its entries through a separate Core Change Approval.
- **Additional optimization candidates:** A `profile` line in publication `prepare` and `diagnose` output would give the same visibility for the planning surface; it is left out to keep this PR to the approved `doctor` surface. A pinned profile schema test could be added when the first relaxation lands.
