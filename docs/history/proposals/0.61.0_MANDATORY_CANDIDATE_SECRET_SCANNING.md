# Core Change Proposal: Mandatory Candidate Secret Scanning

## Purpose

Make the existing AIPS secret scanner a mandatory deterministic security check for every Remote Git publication candidate, including secrets introduced and later removed within its commit range.

## Why this is a Core Change

The change updates publication security semantics and fail-closed behavior. It reuses the current scanner and Integration Gate; it does not add a new authority or alter the Constitution.

## Approved Scope

### In scope

- Central secret-scan policy with detector-aware lockfile handling and expiring fingerprint allowlist.
- Strict publication mode with no inline bypass; exact final-tree plus `base..head` history scan.
- Required Integration Gate check, candidate/policy/scanner evidence binding, local preflight integration and CI fail-fast scan.
- Redacted failure evidence, lifecycle and contract tests, Scenario 176, documentation placement, architecture and release metadata updates to v0.61.0.

### Out of scope

- New Role, Skill, Capability, Constitution Article or independent Approval Gate.
- Required GitGuardian/Gitleaks account, API key, GitHub App or other external scanner credential.
- Automatic secret rotation, remediation, merge approval or publication authority.

## Impact

### Architecture / Contracts

Existing publication flow gains a mandatory built-in scan before expensive CI dependencies and as required Integration Gate evidence. The current `repository` required context and Git Publish Approval authority remain unchanged.

### Data / Migration

No product data, database, schema migration or persistent service state. Scanner reports contain only paths, lines, detector IDs, truncated fingerprints and hashes.

### Security / Reliability

Strict mode scans final committed content and all reachable commits in `base..head`, honors only central path/detector/fingerprint exceptions with expiry, and blocks incomplete scans. Lockfiles suppress only the generic assignment detector. External scanners remain optional.

### Compatibility / Rollback

No public API or configuration migration. A candidate that previously passed without a secret-scan result will now block until rescanned. Rollback is a code/config revert; it must not silently restore publication without mandatory scan evidence.

### Tests / Validation

See `.aips/review/CORE_CHANGE_TEST_MATRIX.yaml`. Recompute on any new behavior-bearing path or security boundary. Required release evidence: secret lifecycle evidence, relevant static/contract checks, documentation closure, repository validation and exact-candidate Integration Gate.

## Risks

- False positives can block publication; central fingerprint/path/detector exceptions with expiry provide bounded reviewable handling.
- History scanning increases work with large candidate histories; file-size limits fail closed and are policy-controlled.
- Strict UTF-8 text scanning does not inspect known binary formats; those remain listed in the scanner contract and may use platform-side defense-in-depth.

## Recommendation

Approved implementation: reuse the built-in scanner, make the invariant mandatory in the existing Integration Gate, and keep third-party scanners optional.

## Proposed Implementation Order

2. Bind the required Integration Gate check to candidate, policy and scanner hashes.
3. Add local preflight and early CI scan.
4. Add lifecycle/contract/scenario evidence and update docs/placement/version.
