# v0.50.0 — Governance Audit Retention & Verification Policy

## System Improvement Review

Appropriateness: ADOPT with bounded modification.
Problem: v0.49 can produce independently anchored portable audit bundles, but it does not provide deterministic discovery across many bundles, checkpoint key-rotation accounting, or a governed retention review lifecycle.
Reuse: extend the existing Governance Audit evidence surface. Do not add a Role, Skill, Capability ID, remote service, database or approval gate.
Recommended solution: add a deterministic catalog/retention helper plus machine-readable policy. The helper verifies bundles at registration, builds a provenance catalog, validates checkpoint key identity across rotations, supports deterministic lookup, and emits advisory retention plans.
Authority: no automatic deletion or compaction. Expiry means REVIEW_DUE only. Legal hold wins. Human approval is required for any later destructive action.
Security: catalog stores digests/fingerprints and observable provenance only; it does not persist source absolute paths, HMAC material or signing private keys.
Compliance boundary: configured durations are AIPS operational defaults, not legal/regulatory retention requirements.
Constitution impact: NO.
Architecture impact: existing governance-security surface and detailed Human/Agent architecture docs are affected; no new top-level runtime plane.

## Core Change Scope

In scope:
- config/governance-audit-retention.yaml advisory policy;
- scripts/governance_audit_retention.py commands: catalog-build, catalog-verify, catalog-find, retention-plan;

- fail-closed key-id/fingerprint mismatch detection;
- external-anchor requirement by SAL;
- SAL 4 signed-checkpoint registration requirement;
- legal-hold precedence;
- minimal digest record generation after review threshold;
- Scenario 160 lifecycle evidence and documentation synchronization.

Out of scope:

- cloud/object-store integration;
- database/search service;
- blockchain/timestamp service;
- automatic legal-compliance claims;
- key generation/rotation authority;
- new Agent/provider credential requirement;
- VERSION/CHANGELOG finalization before feature and protected-main validation.

Data/migration: additive. Existing v0.48 ledgers and v0.49 bundles remain valid.
Rollback: remove the new helper/config/template/tests and v0.50 references; v0.49 bundle verification remains intact.
Human approval: current request explicitly authorizes implementing the recommended direction and running the Git update flow.
