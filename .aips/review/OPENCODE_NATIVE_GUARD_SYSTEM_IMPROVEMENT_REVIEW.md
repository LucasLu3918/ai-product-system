# System Improvement Review: OpenCode Native Context and Guard

## Review

- **Appropriateness:** 有條件適合。OpenCode V2 provides native hooks for prompt context, tool execution, permission evaluation, and shell creation. Implement only the boundaries that can be locally exercised and state unsupported paths honestly.
- **User problem:** AIPS prompt routing conflates domain, intent, and effect; Chinese creative asset requests can select incomplete context; OpenCode receives projected guidance but cannot inject current project readiness or guard supported native writes.
- **Proposed solution:** Implement all four recommendation phases from the referenced conversation: separate classification dimensions and creative asset routing; add a V2 native plugin; connect readiness and policy context with conservative path/symlink/evidence/cache handling; add lifecycle, failure, and performance evidence.
- **Existing coverage:** `scripts/turn_intent.py` routes broad categories and mutation; Project Intelligence Context Manifest already reports readiness; `scripts/opencode_skill_projection.py` safely owns native projections; current runtime policy handles established high-risk external action classes but does not define local file-write authorization.
- **Reuse / extension candidates:** Extend turn-intent classification, Context Manifest, existing OpenCode owned-file installation, CLI harness, compatibility contract, and current lifecycle evidence. Keep existing Creative Skills and runtime policy boundaries.
- **Lower-layer alternative:** Markdown instructions alone cannot deliver fresh per-turn context or enforce a native pre-tool decision. A project-local plugin would miss global AIPS use; a global V2 plugin is the narrow supported layer.
- **Context / token cost:** Inject compact context immediately before model dispatch, with per-session/project fingerprint caching and bounded manifest output. Do not persist raw prompts or add a new global Role/Skill.
- **Security / reliability:** Restrict enforcement claims to directly inspected native OpenCode tools and exact tested operations. Resolve paths and symlinks under project root; missing/stale readiness blocks affected writes; plugin error must be visible and fail closed for supported direct writes. Shell subprocesses, arbitrary custom tools and MCP writes remain outside the proven guard unless independently intercepted and tested. Do not broaden `runtime_policy.py` external-egress semantics.
- **Backward compatibility:** Preserve V1 projection behavior and current native files. Install the plugin only when an explicit/verified V2 runtime is detected. Preserve unowned or changed files and JSONC; unknown version, damaged ownership, plugin failure or unsupported operation reports conflict/unknown rather than claiming enforcement.
- **Scenario / test impact:** Add prompt dimension and Chinese creative routing vectors; direct SVG/image read versus conversation versus create/edit; readiness unavailable/partial/stale, symlink/path escape, non-Git playground, plugin error, shell and MCP limits; install/update/doctor/uninstall/version and idempotency lifecycle. Add one new conformance scenario and retain current scenarios.

- **Agent docs impact:** Update adapter registry, canonical adapter contract, capability registry, documentation placement/sync, Project Intelligence topics and scenario references.
- **Architecture diagram impact:** Update runtime/OpenCode integration and policy-boundary diagrams only where they currently imply static projection or omit the new native hook. Keep generated architecture projections derived from capability registry.
