# v0.56.0 CI-Parity Publication Preflight

## Decision

Conditionally suitable and accepted as an extension of the existing Integration Gate capability. The implementation centralizes candidate resolution and ordering without creating a second test framework or granting publication authority.

## Problem

Local validation and GitHub Actions could initially disagree because they resolved base revision, change class, documentation diff base, matrix selection and environment prerequisites at different stages. A squash merge could also leave a tree-equivalent local `main` on a different commit, making the next validation start from confusing history.

## Change boundary

- Shared publication plan/run entrypoint used by local CLI and GitHub Actions.
- Fast diff/documentation checks before expensive lifecycle validation.
- Environment capability diagnostics and protected-branch route reporting.
- Safe, explicit post-merge reconciliation and equivalent-tree Project Intelligence refresh.
- Documentation audience handling for Git-ignored local metadata.

## Authority and safety

The preflight is deterministic and advisory until the existing Integration Gate runs. It cannot approve, push, merge, reset, release or deploy. Reconciliation requires an explicit apply request, a clean target-branch checkout and identical local/remote tree objects; it creates a backup branch before reset. Project Intelligence metadata is refreshed only for tree-equivalent commits.

## Verification

Scenario 165, focused lifecycle evidence, repository static contracts, CI-parity Integration Gate and protected-main validation bind the exact candidate. The canonical Core Change Test Matrix records applicability and evidence for every affected boundary.
